# ADR-004: shadcn/ui (Radix + Tailwind + cva) como biblioteca de UI padrão

**Data:** 23/06/26
**Status:** Aceita
**Decisores:** Humano (thiagoroddev), IA (agente geral-robusto)

## Contexto

A direção de produto (ADR-002 roteamento local, ADR-003 app shell mobile-first com React Router; rascunhos `fluxo-roteirizacao.md` e `draft-roteirizador-a-pe.md`) exige uma **UI rica e mobile-first**: bottom tab bar, header, painéis de ação por contexto, HUD, cards "Etiqueta", toggle segmentado, dialogs, modo execução tela cheia, tudo empacotado como **TWA na Play Store**, com **assinatura premium**.

Até aqui o projeto não tinha biblioteca de UI: usava Tailwind com um sistema de tokens **próprio** (`primary/secondary/success/warning/danger/bg/surface/text/muted/border`) e componentes que montavam estilos à mão, alguns com texto/estrutura repetidos. Sem um design system, a tendência é "força bruta": componentes não reutilizáveis, difícil de um humano manter sem IA.

O módulo 13 do pacote (`UI e Design System`) **recomenda shadcn/ui + Radix** e exige componentização (`forwardRef`, `className`, `cva`, tokens, zero lógica de negócio).

## Decisão

**Adotamos shadcn/ui (Radix UI + Tailwind + `cva` + `cn`) como biblioteca de UI padrão do projeto.**

- Componentes vivem em `src/components/ui/` (copiados para o repo, ou seja, **somos donos do código**), nomes/props em **inglês** (ADR-001), texto de usuário sempre via `UI_LABELS`.
- **Sistema de tokens padrão do shadcn** (CSS variables: `background/foreground/card/popover/primary/secondary/muted/accent/destructive/border/input/ring/radius`), **substituindo** o sistema de tokens custom anterior, sem manter dois sistemas (sem "remendo"). A cor de marca (laranja Shopee) vira `--primary`.
- Add-ons: **`lucide-react`** (ícones de UI), **`vaul`** (drawer/bottom-sheet mobile) quando necessário; Radix por componente.
- **Componentização e DRY são inegociáveis** (módulo 13 + Regra de Três): nada de classes Tailwind hardcoded fora dos tokens; criar componente novo em `components/ui/` quando não houver; wrappers conforme módulo 13.

O **mapa** (Leaflet + ícones SVG) permanece custom: nenhuma lib cobre o sistema de marcadores; é o diferencial e fica em `components/[domínio]/`, ainda assim componentizado.

## Consequências

### Positivas
- **Manutenção humana:** o componente é React+Tailwind legível no próprio repo; um humano abre e edita sem depender de IA nem de mágica de npm.
- **Acessibilidade** dos widgets complexos (Dialog, Popover, Dropdown, Toggle Group, Tabs) via Radix.
- **Bundle enxuto / tree-shakeable**, o que importa para TWA/Play Store (performance).
- **Não impõe navegação**, então convive com o React Router (ADR-003).
- Tokens semânticos via CSS vars → tema claro/escuro e i18n de marca num lugar só.

### Trade-offs Aceitos
- **Deps novas:** `clsx`, `tailwind-merge`, `class-variance-authority`, `lucide-react`, `tailwindcss-animate` (+ Radix por componente). Pequenas, padrão do ecossistema.
- **Refatoração do tema + componentes existentes:** o sistema de tokens custom é substituído; os componentes do modo Visualizar migram para shadcn/tokens. Aceito (decisão "sem remendos").
- **Manutenção manual de updates** dos componentes (você é dono). Aceito: é o ponto.

## Alternativas Descartadas

### Ionic React
- Traz roteamento/navegação próprios → conflita com ADR-003 (React Router). Framework pesado, lock-in, contraria "ser dono do código".

### Material UI (MUI) / Chakra
- Vêm como pacote npm com tema "mágico" e CSS-in-JS; brigam com Tailwind e com o objetivo de manutenção-humana transparente.

### Manter Tailwind puro + tokens custom
- É o estado anterior; sem primitivos acessíveis prontos, reinventa modal/dropdown/combobox (anti-padrão do módulo 13).
