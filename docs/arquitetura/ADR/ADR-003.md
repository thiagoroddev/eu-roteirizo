# ADR-003: App shell mobile-first com navegação por abas (React Router)

**Data:** 22/06/26
**Status:** Aceita
**Decisores:** Humano (thiagoroddev), IA (agente geral-robusto)

## Contexto

O app nasceu como **SPA de página única**: `App.tsx` renderiza `RouteViewer` diretamente, **sem roteador** (há um React Router comentado, não usado), conforme registrado em `docs/contexto-projeto-ai.md`. Era suficiente para um visualizador único.

A direção de produto mudou (ADR-002, visão "roteirizador a pé", foco B2C empacotado como TWA — ver `analise-comercial-2.0.md` §10). Um app mobile na loja precisa de um **shell**: header (título + engrenagem + voltar), **barra de navegação inferior** (abas) e múltiplas telas (planejar/executar no Mapa, gerenciar Rotas salvas). Isso exige **navegação real**:

- o **botão voltar de hardware do Android** (TWA) precisa funcionar de forma previsível;
- as telas precisam de identidade própria (rota/URL) para histórico e futuros deep links.

A prototipação de alto nível tornou essa lacuna evidente (faltava header/menu inferior e a definição das telas).

## Decisão

**Adotamos `react-router-dom` e um app shell mobile-first com navegação por abas.**

- **Shell:** header fixo (título + engrenagem de configurações + voltar quando aplicável) e **bottom tab bar**.
- **Abas no MVP:** **Mapa** (`/` — importar, planejar manual/auto, salvar, executar) e **Rotas** (`/rotas` — lista de rotas salvas, executar, importar/exportar). **Relatórios** e **Perfil** ficam como **stubs** para depois.
- **Configurações de Rota** (raio, velocidades) abrem pela **engrenagem do header**, não são aba.

Esta ADR **atualiza** a decisão "SPA de página única / sem router" descrita em `docs/contexto-projeto-ai.md` (que deve ser sincronizado — TASK-DOC gerada).

## Consequências

### Positivas

- Botão voltar do Android e histórico funcionam de forma padrão (essencial no TWA).
- Telas com URL própria → base para deep links futuros.
- Estrutura clara separa **planejar/executar** (Mapa) de **gerenciar** (Rotas), facilitando a evolução.

### Trade-offs Aceitos

- **Dependência nova** (`react-router-dom`): aceita e aprovada; é o padrão de fato, pequena e estável.
- **Reescrita do `App.tsx`** para introduzir o shell + rotas: aceito; o `RouteViewer` atual vira a tela do Mapa.
- **Reverte a simplicidade "SPA única"**: aceito porque o produto agora é multi-tela por necessidade real.

## Alternativas Descartadas

### Alternativa 1: Troca de view por estado (useState/Context, sem lib)

**Por que descartada:**
- Botão voltar do Android e histórico ficam manuais e frágeis conforme as telas crescem.
- Sem URL por tela; deep links inviáveis.

### Alternativa 2: Hash router caseiro

**Por que descartada:**
- Reinventa, mal, o que o React Router já faz; manutenção desnecessária.
