# ADR-002: Roteamento local sobre grafo OpenStreetMap (sem API de roteirização)

**Data:** 22/06/26
**Status:** Aceita
**Decisores:** Humano (thiagoroddev), IA (agente geral-robusto)

## Contexto

Surgiu uma nova direção de produto para a aplicação (hoje um visualizador de rotas): evoluí-la para um **roteirizador de paradas a pé**, voltado à realidade de quem entrega caminhando em paradas próximas(caso de uso: entregador Shopee). A visão completa está em [`docs/rascunhos/draft-roteirizador-a-pe.md`](../../rascunhos/draft-roteirizador-a-pe.md).

Um requisito central dessa visão é, **durante o planejamento**, traçar o caminho **pelas ruas, respeitando o sentido das vias (mão única)**, exibindo a quilometragem real percorrida e permitindo trocar o ponto de destino para comparar rapidamente por quais ruas se passaria. Isso é, tecnicamente, um motor de roteamento sobre malha viária.

A restrição de produto é **baratear**: não depender de API paga de roteirização (Google Directions, Mapbox Directions). Discutimos dois níveis de ambição:

- **Nível A:** sugerir ordem por proximidade (linha reta) e **delegar a navegação real ao Google Maps/Waze** via deep links. Não desenha o traçado fiel às ruas dentro do app.
- **Nível B:** o próprio app calcula e desenha o traçado que respeita a mão de direção, localmente, sobre dados de via abertos.

O Nível A **não atende** o requisito de ver, no planejamento, a rua traçada com quilometragem e comparar destinos pelas vias percorridas. Por isso a questão: é viável fazer o Nível B sem API de roteirização, e a que custo?

Para decidir com base em evidência, e não em suposição, foi construído um protótipo descartável (TASK-RF-001) e validado em campo (Ipanema/RJ).

## Decisão

**Adotamos roteamento local sobre grafo do OpenStreetMap (Nível B) como abordagem do roteirizador, sem usar API de roteirização.**

Concretamente:

1. **Os dados de via vêm do OpenStreetMap** (via Overpass API ou extract pré-baixado). Obter o *dado bruto* das ruas é permitido pela restrição; o que se evita é a API que *calcula a rota*.
2. **O grafo é direcionado:** cada trecho de rua vira aresta(s) entre nós (cruzamentos); a tag `oneway` determina o sentido. A mão única vira **ausência da aresta no sentido proibido**, então a restrição emerge da estrutura de dados, não de lógica defensiva.
3. **O menor caminho é calculado localmente** (A\*/Dijkstra), no cliente, sem servidor de roteamento próprio nem API externa de cálculo.

A migração para o código de produção será incremental e parametrizada por tarefas futuras; esta ADR fixa a **abordagem**, não a implementação final.

## Consequências

### Positivas

- **Atende o requisito central** (traçado fiel à rua + quilometragem + comparação de destinos no planejamento), o que o Nível A não faz.
- **Custo recorrente ~zero:** OSM é aberto; o cálculo roda no cliente. Sem mensalidade de API de rota.
- **Diferencial de produto:** paradas a pé com traçado real respeitando contramão, ausente nos apps pagos para esse caso.
- **Offline-friendly:** combina com a natureza PWA do app (grafo cacheável em IndexedDB).
- **Sem contramão por construção:** como a aresta proibida não existe no grafo, nenhum caminho sugerido viola a mão de direção.

### Trade-offs Aceitos

- **Pipeline de dados é o grosso do esforço:** baixar/filtrar OSM, montar o grafo, lidar com tamanho e offline, e *map matching* (encaixar o ponto de entrega no nó de rua). Aceito: é onde mora ~80% do trabalho, mas foi validado como factível.
- **Qualidade depende do OSM:** se a tag `oneway` estiver incorreta/ausente numa via, o traçado herda o erro. Aceito; mitigável com correção colaborativa no OSM e checagens.
- **A\* didático não escala sozinho:** a versão de protótipo varre a fronteira linearmente; produção exigirá fila de prioridade (heap). Aceito como item de implementação, não de viabilidade.
- **Dependência de um serviço público (Overpass):** sujeito a indisponibilidade momentânea. Aceito; mitigável com extract pré-processado/cache.

## Alternativas Descartadas

### Alternativa 1: API de roteirização paga (Google Directions / Mapbox)

**Por que descartada:**
- Contraria a restrição central de baratear (custo por requisição / limites de cota).
- Gera lock-in e dependência de chave/billing para a função-núcleo do produto.

### Alternativa 2: Apenas Nível A (linha reta + delegar navegação ao Maps/Waze)

**Por que descartada:**
- Não entrega o requisito de ver a rua traçada com quilometragem e comparar destinos pelas vias **no planejamento**, que é exatamente o diferencial pretendido.
- (Os deep links para Maps/Waze permanecem úteis na *execução* da rota, mas como complemento, não como o motor de planejamento.)

### Alternativa 3: Servidor de roteamento self-hosted (OSRM / Valhalla)

**Por que descartada (por ora):**
- Reintroduz um backend/serviço a manter, contrariando a arquitetura 100% client-side do app e o objetivo de custo baixo.
- Overkill para o escopo atual; o cálculo local no cliente já se mostrou viável no protótipo.
