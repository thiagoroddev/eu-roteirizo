# ADR-007: Estratégia de basemap (tiles): provedor com TOS comercial atrás do Worker, com cache e anti-leech

**Data:** 25/06/26
**Status:** Aceita (princípio); escolha do provedor específico = item aberto
**Decisores:** Humano (thiagoroddev), IA (agente geral-robusto)

## Contexto

A imagem de fundo do mapa (**tiles**) é servida por um **Cloudflare Worker** (`infra/cloudflare-tile-worker/worker.js`, ver RNF-12) que hoje faz proxy de **`https://tile.openstreetmap.org/{z}/{x}/{y}.png`**, ou seja, os **servidores públicos do OSM**, com cache de 7 dias (Cache API + edge CF) e bloqueio de `z < 14`.

**Importante:** isto é separado do **roteamento** (ADR-002), que é local e gratuito. Aqui se trata só do *basemap*.

Indo para **produto profissional, nacional, na Play Store** (escopo "app do entregador"), surgem três problemas no estado atual:

1. **Licença/TOS:** a *Tile Usage Policy* do OSM **não permite** uso comercial/pesado dos tiles públicos. Risco de **bloqueio** (por volume/User-Agent) e de **identidade visual genérica**. Pôr cache na frente reduz a carga, mas **não torna o uso compatível**.
2. **Leeching:** o Worker responde com `Access-Control-Allow-Origin: *` e **não valida quem chama**: qualquer app pode apontar para a URL do Worker e **consumir a cota**.
3. **UX do zoom:** `z < 14` bloqueado impede a **visão geral da rota** (cidade inteira, ~z11 a z13).

Ponto positivo: o Worker já é uma boa **camada de cache + abstração**, porque o app só conhece a URL do Worker, não o provedor.

## Decisão

1. **Manter o Cloudflare Worker como camada trocável + cache.** O app continua conhecendo só a URL do Worker; trocar de provedor é mudar o Worker, não o app.
2. **Trocar o upstream** de OSM público para um **provedor com TOS comercial e tier grátis/barato** (candidatos: MapTiler / Stadia / Carto, raster). A **escolha específica fica em aberto** (avaliar tier grátis, TOS, estilo). A **chave vai como secret do Worker** (env/Wrangler), **nunca no cliente**.
3. **Anti-leech:** o Worker valida `Origin`/`Referer` (ou um token do app) e responde 403 a quem não for o app. Opcional: teto diário por IP como disjuntor.
4. **Rever o bloqueio de zoom:** liberar até ~z10 ou z11 para permitir a visão geral da rota; o cache absorve o custo.
5. **A decisão de renderização (raster/Leaflet × vector/MapLibre) e do provedor é da FASE DE VISUAL**, que começa **só quando o motor de roteamento estiver funcional** (decisão do humano, 25/06). Até lá, o mapa segue como está; aqui ficam os candidatos mapeados (abaixo).

### Candidatos de provedor (shortlist avaliada em 25/06)

**Custo:** vetor **não** é mais caro, geralmente é **mais barato** (~4 requests/visualização contra ~10 a 16 do raster, payloads menores). O "custo" do vetor é **esforço** (trocar Leaflet→MapLibre + repensar o cache do Worker para `.pbf`/estilo/sprites) e **curva de aprendizado**, não dinheiro. Dado o estágio inicial (mapa do roteirizar ainda a construir) e a **identidade de marca já definida** (ADR-006, ciano + claro/escuro), **vetor/MapLibre ficou o candidato forte**, a reavaliar na fase de visual.

**Hospedado (rápido para validar, free tier):**
- **MapTiler:** ~100k tiles/mês grátis; **editor de estilo** (tema ciano/claro-escuro); vector + raster; MapLibre-friendly. Melhor "começar hoje".
- **Stadia Maps:** free tier (com atribuição); MapLibre-friendly; preço previsível.
- **Mapbox:** **evitado** (GL JS v2+ proprietário, cobra por *map load*).

**Self-host barato (⭐ destino preferido):**
- **Protomaps / PMTiles em Cloudflare R2 + Worker:** arquivo `.pmtiles` (RJ/SP/Brasil) no **R2**, servido pelo **Worker que já existe**; **sem fatura por request** (só storage + saída), **identidade total** (style JSON do MapLibre), aproveita a **infra Cloudflare atual** e a vantagem de "mesmas áreas sempre".
- OpenMapTiles + TileServer GL (VPS, ~R$250 a R$500/mês): alternativa clássica; mais ops, provavelmente dispensável.

**Caminho recomendado:** MapTiler/Stadia (hospedado, rápido) **→ Protomaps PMTiles em R2** (custo mínimo + controle). Como tudo fica atrás do Worker, migrar é trocar a fonte, não o app.

## Consequências

### Positivas

- **Conformidade** (TOS comercial) e **confiabilidade** (sem risco de bloqueio do OSM público) para o lançamento.
- **Custo baixo:** o cache do Worker + o reuso de área (motoristas no mesmo bairro) fazem só o *cache-miss* chegar ao provedor pago → billing minúsculo.
- **Identidade visual própria** possível (estilo do provedor).
- **Sem lock-in:** provedor trocável (e self-host futuro) atrás do mesmo Worker.

### Trade-offs Aceitos

- Passa a depender de um provedor (com tier grátis/barato) e de gerir uma chave/secret.
- O provedor específico e a renderização (raster×vector) ficam para a **fase de visual** (após o motor), com a **shortlist já mapeada** acima e **Protomaps PMTiles em R2** como destino preferido.

## Alternativas Descartadas

### Alternativa 1: Continuar nos tiles públicos do OSM (com cache)
**Por que descartada:** viola a TOS para uso comercial; risco de bloqueio; visual genérico. Cache não resolve a questão de licença.

### Alternativa 2: MapLibre GL + vector tiles já no MVP
**Por que descartada (por ora):** reescreve a camada de mapa (lib diferente, estilo JSON) sem necessidade de lançamento. "Profissional" vem de tiles confiáveis + marcadores limpos, não de vetor. Fica como fase 2.

### Alternativa 3: Self-host de tiles (OpenMapTiles/TileServer GL)
**Por que descartada (por ora):** dor de cabeça precoce. Previsto como evolução **atrás do mesmo Worker** quando a escala justificar (troca de config, não de app).
