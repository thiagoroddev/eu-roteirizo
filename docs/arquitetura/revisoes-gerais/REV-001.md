## Achados

### REV-001-A01 - docs/arquitetura.md e docs/requisitos.md descrevem um sistema que não existe

- **Severidade:** 🔴 Bloqueante
- **Área:** docs/arquitetura
- **Evidência:** `docs/arquitetura.md:1-35` (título "HubFlow Logistics"; stack Next.js 14 + Prisma + PostgreSQL/Supabase + NextAuth + shadcn/ui + Vercel); `docs/requisitos.md:1-65` (25 RFs: identidade, escalas, marketplace, fila virtual, bipagem). Nada disso existe: o `package.json` é Vite + React 18 SPA (danfojs, leaflet, xlsx, react-select), sem backend, sem banco, sem auth. Único fluxo real: upload de planilha → visualização de rota em mapa + tabelas.
- **Problema:** Viola o princípio inegociável "código é a verdade primária" (núcleo §2.3): documentação que contradiz o código corrompe decisões futuras. Quem ler esses docs como especificação assume um sistema fullstack inexistente.
- **Recomendação:** Decidir o destino desses dois docs. Opções: (a) marcá-los explicitamente como **visão/roadmap futuro** ("HubFlow" = produto-alvo, ainda não implementado), movendo-os para `docs/visao/` ou prefixando um aviso no topo; ou (b) arquivar em `docs/arquivo/` e reescrever a arquitetura/requisitos reais do MVP. Não deletar sem decisão (núcleo §1.3).
- **Tarefa(s) gerada(s):** - (resolvido diretamente nesta sessão; sem tarefa)

### REV-001-A03 - Vazamento de PII (endereços/CEPs) no console em produção

- **Severidade:** 🟡 Importante
- **Área:** segurança
- **Evidência:** `src/utils/excelProcessor.ts:185-228` — `console.info/console.warn` logam, sem flag de debug, dados das linhas ignoradas, incluindo o conteúdo completo das células (`dataRows = ...` na linha 208): endereço de entrega, CEP, bairro, cidade.

### REV-001-A04 - HTML não escapado no tooltip do mapa (vetor de injeção)

- **Severidade:** 🟡 Importante
- **Área:** segurança
- **Evidência:** `src/components/RouteMap.tsx:153-167` — `tooltipContent` é uma string HTML interpolando campos crus do Excel (`DESTINATION_ADDRESS`, `NEIGHBORHOOD`, etc.) e é passada a `marker.bindTooltip(tooltipContent, ...)`, que renderiza HTML.
- **Problema:** Se uma planilha contiver markup no endereço (ex.: `<img src=x onerror=...>`), ele é injetado no DOM. Risco prático baixo (planilha é fornecida pelo próprio usuário), mas é um vetor real, especialmente se a planilha vier de um sistema upstream.
- **Recomendação:** Escapar os valores antes de interpolar (helper de escape HTML) ou construir o tooltip via nós DOM/`textContent` em vez de string HTML.
- **Tarefa(s) gerada(s):** TASK-BG-003 (concluída em 22/06/26 — helper `escapeHtml` aplicado a todas as interpolações do tooltip)
- **ADR(s) gerada(s):** -
- **Requisito/DT gerado:** -
- **Status do achado:** Resolvido

### REV-001-A05 - Divergência de idioma: convenção declarada (PT) vs código (EN)

- **Severidade:** 🟡 Importante
- **Área:** código / convenções
- **Evidência:** Núcleo §2.4 declara "Projeto atual: Português". O código tem identificadores em inglês (`RouteSimpleTable`, `getCommercialBadgeClasses`, `searchAT`, `RowData`) e comentários/docstrings em inglês (`src/App.tsx:3-19`, `src/types/index.ts:2-19`, `src/pages/RouteViewer.tsx:3-25`, `src/utils/excelProcessor.ts:2-5`), enquanto UI labels e alguns comentários estão em português — mistura real.
- **Problema:** A convenção inegociável "idioma único" (§2.4) está sendo violada de forma sistemática. Hoje o código é majoritariamente EN com UI em PT.
- **Recomendação:** Decisão do humano (boa candidata a ADR, pois é cara de reverter): (a) oficializar o padrão de fato — **código/identificadores/comentários em inglês, textos de UI em português** — atualizando o núcleo/contexto; ou (b) traduzir comentários e docstrings para PT mantendo APIs externas em EN. Recomendo (a): é o padrão de fato e o mais barato.
- **Tarefa(s) gerada(s):** TASK-REF-001 (concluída em 22/06/26 — UI centralizada em UI_LABELS; comentários PT→EN)
- **ADR(s) gerada(s):** ADR-001 (idioma do projeto e internacionalização)

### REV-001-A06 - parseCoordinate frágil e descarte silencioso de coordenadas

- **Severidade:** 🟡 Importante
- **Área:** código / robustez
- **Evidência:** `src/components/RouteMap.tsx:32-38` e o consumo em `:117-120`. **Verificado:** o `replace(/\./g,"")` + `/10000000` é intencional (o comentário na :36 confirma que a entrada é inteiro escalado sem ponto, ex.: `-229000000 → -22.9`) — **não é o bug** que a varredura inicial sugeriu. Porém: coordenadas que não casam o formato viram `undefined` e o marcador é descartado **sem nenhum log ou aviso** (`:120` simplesmente pula); e um valor decimal legítimo ("-22.9") produziria silenciosamente uma coordenada errada.
- **Problema:** Falha silenciosa — pontos somem do mapa sem o usuário saber por quê; nenhuma validação de faixa (lat/lng dentro de Rio bounds).
- **Recomendação:** Validar faixa de lat/lng e contar/avisar (não logar PII — ver A03) quantos pontos foram descartados; documentar o formato esperado da coordenada.
- **Tarefa(s) gerada(s):** TASK-BG-004 (concluída em 22/06/26 — validação de faixa via `isWithinRioBounds` + aviso agregado DEV-only)
- **ADR(s) gerada(s):** -
- **Requisito/DT gerado:** -
- **Status do achado:** Resolvido
