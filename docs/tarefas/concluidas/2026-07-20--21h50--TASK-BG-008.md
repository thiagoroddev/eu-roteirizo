## Planejamento Aprovado

**Causa (provada pela medição CHORE-006):** o carregamento de ruas falha com **429 do Overpass** (fila/rate-limit). Amostras: `rede 2,24 km² 4,7 s / 1,5 s · 147 KB` (mesma área e tamanho, tempo 3× → fila) e `erro 2,24 km² 7-8 s` (Overpass enfileira ~8 s e rejeita 429). **Não é payload** (147 KB) nem parse. Correção de raiz = ADR-010 (tileset próprio). Esta tarefa **mitiga** enquanto isso.

**Sintoma do humano:** apagar cache → recarregar → erro; "Tentar de novo" (imediato) falha de novo; só sair do romaneio e voltar carrega. Motivo: o que cura é o **tempo** (o rate-limit expira em segundos), não a remontagem. O retry imediato bate no mesmo muro.

**Decisão (humano):** auto-retry com backoff.

**O que muda:**
- `utils/routing/osm.ts`: `fetchRoadGraph` passa a **retentar sozinho** falhas transitórias (429, 502, 503, 504, timeout, erro de rede) até `MAX_ATTEMPTS` (⚙️ MANUAL KNOB), com **backoff exponencial + jitter**, **respeitando o header `Retry-After`** quando presente (capado). Erro não-transitório (400, parse) não retenta. `totalMs` da medição passa a incluir as esperas → o painel mostra o gap `total vs rede` (sinal claro de retry). `sleep` injetável para teste determinístico.
- ADR-010 §medição: registrar as amostras ruins (429 ~8 s) que **confirmam positivamente** a fila; corrigir a previsão errada de "erro ~30 s de timeout".

**Critérios de aceite:** apagar cache + recarregar passa a **recuperar sozinho** (sem sair/voltar) quando o 429 é transitório; erro só aparece se **todas** as tentativas falharem; não martela o servidor (backoff respeitando Retry-After).

**Riscos:** retentar contra servidor rate-limited pode piorar se agressivo → mitigado por backoff+jitter e respeito ao Retry-After. Espera total maior (o usuário vê "Carregando…" por mais tempo em vez de erro imediato) — é o trade-off desejado.

## Decisões Tomadas

- **Retry dentro do `fetchRoadGraph`**, não numa camada acima. É o único módulo de rede do motor (já impuro: fetch/AbortController/timeout) — o retry pertence ao adaptador de rede. `loadRoadGraph`/`useRoadGraph` não mudam; o retry é transparente para eles.
- **Parse fora do retry.** Um corpo 200 que não é JSON válido é erro **duro** (query ruim / página de erro), não transitório — retorna sem retentar.
- **Sem campo `attempts` na medição.** Cogitei, mas o gap `totalMs vs networkMs` já denuncia o retry no painel (`total 18 s (rede 1,5 s)` = 16,5 s de espera). Evita mexer no shape gravado e na assimetria rede/erro. Menos é mais.
- **Timeout/rede são retryable.** Podem ser transitórios. `Retry-After` capado em `RETRY_MAX_MS` para um valor hostil não congelar o usuário.
- **`sleep` injetável.** Teste determinístico sem relógio real, em vez de fake timers (mais simples com async).

## O Que NÃO Foi Feito (e Por Quê)

- **Endpoint reserva (mirror).** O humano escolheu só o auto-retry; mirror adiciona dependência de outro servidor comunitário (a própria ADR-010 chamou de "adiar o problema"). Fica para depois se o retry não bastar.
- **Retry ao toggling Original↔roteiro após erro.** Depois de um erro, alternar de volta não retenta (o guard do `useRoadGraph` bloqueia o mesmo `attempt`). O botão manual + o auto-retry cobrem o caso; não mexi para não refetchar a cada toggle. Anotado.
- **Correção de raiz (ADR-010).** Continua sendo o tileset próprio; esta tarefa só mitiga.

## Aprendizados Para o Projeto

- **`tsc -b` (build) é mais estrito que `tsc --noEmit` — 3ª vez que morde.** Aqui: `vi.fn(() => Promise.resolve())` infere parâmetros `[]`, e `spy.mock.calls[0][0]` vira erro de índice de tupla só no build. Ao criar um `vi.fn` cujo argumento será inspecionado, **tipar o parâmetro** (`(_ms: number) => …`). Rodar `npm run build` antes de concluir, não só o `--noEmit`.
- **A medição (CHORE-006) pagou o investimento:** transformou "as ruas às vezes não carregam" numa causa nomeada (429/fila) com correção certa (esperar, não remontar). Sem os números, a tentação seria mexer no bbox ou no cache — nenhum dos dois resolveria.
